2. New finding: Pipecat 1.8.0’s VAD is sensitive to buffer boundaries

I inspected VADAnalyzer._run_analyzer in the downloaded 1.8.0 release
, rather than assuming the latest documentation matched it.

Its sequence is:

 1. Process every complete 32 ms analysis window in the incoming buffer.
 2. Update the tentative speech/silence counters.
 3. After the loop finishes, check whether to confirm SPEAKING or QUIET.

Consequently, a qualifying speech run can reach six windows, then be reset by a failing window
within the same incoming buffer, before speech is confirmed.


Offline reproduction

I executed the release’s actual state-machine method with controlled confidence scores and volume fixed above its
gate.



 Test                                                                                            Result

 Six passing confidence windows followed by two failing windows, delivered one window per call   SPEAKING observed

 The same score sequence, delivered using 3,032-byte input buffers                               No SPEAKING observed

 Sustained passing confidence, using 3,032-byte buffers                                          SPEAKING observed


These are state-machine tests, not Silero speech-recognition tests.
They prove buffer-dependent behavior, not that this caused Lauren’s failed calls.

The handoff’s reported 3,032-byte frame represents 94.75 ms
of mono PCM16 at 16 kHz—almost three VAD windows. That makes the behavior relevant to this pipeline.

4. Extend the investigation through OpenAI’s commit boundary

Pipecat’s local-VAD mode sends audio to OpenAI, then commits the buffer when it receives
VADUserStoppedSpeakingFrame
. Without that event, buffered audio may never produce the expected finalized transcription. This behavior is both
documented and present in the inspected 1.8.0 source. [5]

“Connected and ready” is not a transcription-path test.

The next diagnostic should trace these boundaries:



 Boundary                   Evidence to record

OpenAI documents explicit buffer commits and transcription completion events; completion events should be
correlated using item_id. [6]

5. Elevate hangup and duration enforcement before another test

The missing watchdog plus known broken application-side hangup should not remain minor cleanup.


Telnyx can enforce a carrier-side duration limit

The dial API supports time_limit_secs
, measured after answer. Telnyx terminates the call when the limit is reached and emits acall.hangup
 event with cause time_limit. The documented range is 30–14,400 seconds. [8]

For a short diagnostic, use an explicitly approved short limit within the existing ten-minute ceiling. This protects
against an application stall, but does not replace provider-session cleanup.


The proxy failure has a concrete explanation

Pipecat 1.8.0’s serializer creates aiohttp.ClientSession() without proxy configuration. Aiohttp does not
read proxy environment variables by default; trust_env=True or explicit proxy configuration is needed. [9]

Route hangup through the approved proxy path, use bounded timeouts, and verify termination—not merely that a
hangup request was attempted.

A duration limit is not a $1 spending guarantee.
The budget must include telephony, STT, LLM, and TTS usage, with bounded generation and shutdown behavior.
Balance deltas and estimated cents do not demonstrate an enforced cap.
